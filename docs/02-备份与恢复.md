# 备份与恢复指南

> 备份是生产环境的**生命线**。没有备份的系统，随时可能让你损失所有数据。

---

## 为什么要备份

ERPNext 存着你的客户、订单、财务数据。一旦丢失：

- 硬盘损坏 → 全完
- 误操作删了数据库 → 全完
- 升级出问题 → 可能要回滚
- 被攻击加密 → 有备份就不用付赎金

**不备份 = 赌你的数据不会丢。** 这不是一个值得赌的事情。

---

## 双重备份策略

本方案采用两层备份，互相补充：

| 备份层 | 保护粒度 | 什么时候用 |
|--------|---------|-----------|
| **应用层备份**（bench backup） | 单个站点 | 日常恢复、误删数据、版本回退 |
| **整机备份**（PVE vzdump） | 整个系统 | 系统崩溃、硬盘故障、迁移服务器 |

**两者的关系**：应用备份用于快速（恢复一个站点 5 分钟），整机备份用于救命（恢复需要重搭环境）。

---

## 应用层备份（每天 02:00）

### 备份了什么

备份脚本 `backup.sh` 创建类似这样的目录：

```
~/erpnext/backups/
  └── 2026-05-27_02-00-01/          ← 备份时间
      ├── backups/                   ← 数据库和附件（从容器复制出来的）
      │   ├── 20260527_073001-rc_sh_pve-site_config_backup.json
      │   ├── 20260527_073001-rc_sh_pve-database.sql.gz    ← 数据库
      │   ├── 20260527_073001-rc_sh_pve-files.tar.gz       ← 附件
      │   └── 20260527_073001-rc_sh_pve-private-files.tar.gz
      ├── sites-config.tar.gz        ← 站点配置
      ├── compose.yaml               ← Docker 编排文件
      ├── .env                       ← 环境变量
      ├── compose.lxc.yaml           ← LXC 适配配置
      └── tuning.cnf                 ← MariaDB 配置
```

### 手动执行备份

```bash
cd ~/erpnext
bash backup.sh
```

如果报错，加 `bash -x backup.sh` 查看详细执行过程。

### 查看备份是否成功

```bash
# 查看所有备份
ls -lt ~/erpnext/backups/

# 查看最近一次备份的内容
ls -la ~/erpnext/backups/$(ls -t ~/erpnext/backups/ | head -1)/

# 查看备份大小
du -sh ~/erpnext/backups/$(ls -t ~/erpnext/backups/ | head -1)/

# 查看备份日志
tail -30 ~/erpnext/logs/backup.log
```

### 定时备份

备份脚本配置在 crontab，每天凌晨 2:00 自动运行：

```bash
cat /etc/cron.d/erpnext
# 输出：0 2 * * * root /root/erpnext/backup.sh > /root/erpnext/logs/backup.log 2>&1
```

### 保留策略

- 本地保留最近 **7 天**的备份
- 超过 7 天的自动删除
- 如果磁盘空间紧张，可以改为 3 天

## PVE 整机备份（每天 04:00）

如果你在 PVE 上运行 LXC 容器，整机备份是终极保险。

PVE 备份在**宿主机层面**创建整个 LXC 容器的快照，意味着操作系统、Docker、所有配置和数据全部一起备份。

### 检查备份状态

```bash
# 在 PVE 宿主机上执行
pvesh get /cluster/backup
```

### 手动触发整机备份

```bash
vzdump 100 --mode snapshot --compress zstd --storage hdd
```

| 参数 | 说明 |
|------|------|
| `100` | LXC 容器的 ID |
| `--mode snapshot` | 快照模式，备份期间不中断服务 |
| `--compress zstd` | 使用 zstd 压缩（比 gzip 快，压缩率更高）|
| `--storage hdd` | 备份存到 hdd 存储 |

### 查看整机备份文件

```bash
ls -lh /mnt/storage/dump/
# 输出：vzdump-lxc-100-2026_05_27-11_06_40.tar.zst
```

## 三种恢复场景

### 场景一：恢复单个站点数据（最常见的场景）

用户误删了数据，或升级出了问题想回退。

```bash
# 1. 找到最近的备份文件
ls -lt ~/erpnext/backups/*/backups/*.sql.gz
# 选一个日期最近的

# 2. 进入工作目录
cd ~/erpnext/frappe_docker

# 3. 停止所有服务（防止恢复期间数据被写入）
docker compose stop backend queue-short queue-long scheduler websocket

# 4. 执行恢复
docker compose exec -T backend \
  bench --force --site erpnext.example.com \
  restore /path/to/备份文件.sql.gz

# 5. 迁移（更新数据库结构）
docker compose exec backend bench --site erpnext.example.com migrate

# 6. 清缓存
docker compose exec backend bench --site erpnext.example.com clear-cache

# 7. 恢复服务
docker compose start

# 8. 验证
docker compose exec backend bench --site erpnext.example.com doctor
```

### 场景二：完整恢复站点（含附件和配置）

备份 + 站点配置 + 附件全部恢复。

```bash
# 1. 如果需要，创建目标站点
docker compose exec backend \
  bench new-site erpnext.example.com \
  --admin-password "管理员密码" \
  --db-root-password "数据库密码"

# 2. 解压配置备份
tar -xzf ~/erpnext/backups/日期/sites-config.tar.gz

# 3. 恢复站点配置
# 把备份中的 site_config.json 复制到容器内
docker compose cp ~/erpnext/backups/日期/sites-config/erpnext.example.com/site_config.json \
  backend:/home/frappe/frappe-bench/sites/erpnext.example.com/site_config.json

# 4. 恢复数据库
docker compose exec -T backend \
  bench --force --site erpnext.example.com \
  restore ~/erpnext/backups/日期/backups/*-database.sql.gz

# 5. 迁移 + 清缓存
docker compose exec backend bench --site erpnext.example.com migrate
docker compose exec backend bench --site erpnext.example.com clear-cache
```

### 场景三：整机灾难恢复（系统完全崩溃）

PVE 宿主机上操作：

1. 登录 PVE Web 界面
2. 左侧选中你的 LXC 容器
3. 点 **Backup** 标签
4. 选择要恢复的备份（按时间找最近的）
5. 点击 **Restore**
6. 勾选确认，开始恢复
7. 恢复完成启动容器，检查服务

```bash
# 容器启动后，登录进去
pct start 100
ssh root@容器IP

# 检查服务
cd ~/erpnext/frappe_docker
docker compose ps
docker compose logs --tail=20
```

## 加密密钥（重要）

如果你的站点启用了文件加密（旧版的 ERPNext 可能开启了），恢复后需要处理加密密钥。

```bash
# 1. 查看旧备份中的 site_config.json 是否有 encryption_key
grep encryption_key ~/erpnext/backups/日期/sites-config/erpnext.example.com/site_config.json

# 如果包含 encryption_key：
# 2. 复制到新站点的配置中
docker compose exec backend bash
# 现在在容器内部：
cat sites/erpnext.example.com/site_config.json
# 手动把 encryption_key 加到配置中
```

没有加密密钥的话，已加密存储的附件会无法读取。

## 恢复验收清单

恢复完成后逐项检查：

- [ ] 网页能正常访问（`curl http://localhost/`）
- [ ] 能登录（Administrator + 密码）
- [ ] 打开几个旧单据/客户数据，确认数据完整
- [ ] 附件/上传的文件能下载打开
- [ ] 搜索功能正常
- [ ] 打印格式正常
- [ ] 报表能正常生成
- [ ] 检查备份日志没有报错

## 异地备份（进阶）

本地备份有一个致命问题：**如果服务器硬盘坏了，本地备份也跟着没了**。

建议在有条件时增加异地备份：

### rsync 到远程服务器

```bash
# 需要一台远程服务器或者 NAS
rsync -avz --delete ~/erpnext/backups/ user@远程IP:/backup/erpnext/
```

### cron 自动同步

```bash
# 每��备份完成后同步到远程
echo '30 2 * * * root rsync -avz --delete ~/erpnext/backups/ user@远程IP:/backup/erpnext/' \
  | sudo tee /etc/cron.d/erpnext-remote
```

这会每天凌晨 2:30（备份完成后 30 分钟）自动同步。

## 备份最佳实践

- ✅ **每天检查**备份日志（看一眼 `tail -5 ~/erpnext/logs/backup.log` 就行）
- ✅ **每周抽一次**：试着解压一个备份文件，看看里面数据对不对
- ✅ **每月做一次**完整恢复演练（在测试环境试一下真正恢复）
- ❌ 不要等到出事了才想起来没验证过备份
